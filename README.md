# INFR3120 Group Project – Part 1

## What this contains
Express/EJS setup, MongoDB connection, shared booking model, validation, overlap check, booking creation, and Render configuration. The landing page is only a placeholder. A separate local-only EJS demo at `/demo` saves test bookings and lists resource schedules without displaying student information. Part 2 handles study-room pages; Part 3 handles equipment pages, shared layout, bookings table and confirmation email.

## Run locally
1. Install Node.js 22 and have a MongoDB server or Atlas database available.
2. Open this folder in VS Code and run `npm install`. Retain the package-lock.json generated by npm in the group repository.
3. Copy `.env.example` to `.env` (`Copy-Item .env.example .env` in PowerShell). Set MONGODB_URI to your own database connection string. The default works only if a local MongoDB server is running. Never commit `.env`.
4. Run `npm start` and visit http://localhost:3000. Visit /health to confirm the database is connected. Click the Part 1 booking demo link, or visit http://localhost:3000/demo. Use a dedicated test database.
5. Run `npm test` for validation, overlap-query, simultaneous request and queue recovery tests. They do not require a live database.

## How the files work
- `app.js`: Express configuration, EJS, middleware, routes and error handling.
- `server.js`: reads the environment, connects to MongoDB, and starts the server. It is named server.js to match the A2 reference scaffold.
- `config/database.js`: MongoDB connection.
- `models/booking.js`: Mongoose booking schema for both resource types.
- `lib/validateBooking.js`: checks fields, email, date and time format.
- `lib/createBooking.js`: looks for overlapping bookings and saves only valid, non-conflicting ones.
- `routes/api.js`: temporary POST test endpoint.
- `routes/demo.js`, `views/backend-demo.ejs`, `views/partials/demo_header.ejs`, `views/partials/demo_footer.ejs`: local test form and schedule table only. These follow the EJS partial structure from A2 and do not replace the group landing page.
- `routes/index.js`, `views/index.ejs`, `views/error.ejs`: minimal placeholders to run the app.
- `render.yaml`: optional Render Blueprint configuration.

## Test the database with a sample booking
With the server running in development and ENABLE_DEMO=true, open a second PowerShell terminal. Run the following using dummy data (change the date/resource ID if already used):

```powershell
$body = @{
  bookingType = 'room'
  resourceId = 'room-101'
  studentName = 'Test Student'
  studentNumber = '100000001'
  email = 'test@example.com'
  date = '2027-01-15'
  startTime = '10:00'
  endTime = '11:00'
} | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri 'http://localhost:3000/api/bookings' -ContentType 'application/json' -Body $body
```

Expected first response: status 201 and a MongoDB ID. Run it again: status 409. Change the time to 11:00–12:00: expected 201. Try an invalid email: expected 400. Verify the saved document in MongoDB. These are manual test steps, not results from an actual database run.

## Render deployment
1. Push the project to the group's GitHub repository (never include `.env` or node_modules).
2. Create a Node web service linked to the repository, or use the included render.yaml as a Blueprint. Select the directory containing package.json if your repository has other folders.
3. Set the build command to `npm install` and the start command to `npm start`. Set MONGODB_URI and NODE_ENV=production in Render's environment settings. Render provides PORT automatically.
4. Ensure MongoDB permits connections from your Render service and uses an appropriate database user. Never put credentials in the README or repository.
5. Deploy and check the service logs and /health URL. The temporary demo and API are disabled in production; use the merged team booking routes to test the deployed application with dummy data.
